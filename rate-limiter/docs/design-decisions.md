# 设计决策与已知局限

本文档详细分析限流器项目在并发安全、架构层面的设计取舍与已知局限，帮助理解项目在生产环境中的边界。

---

## 1. 并发安全保证

### 1.1 算法层：`sync.Mutex` 保证 Check-then-Act 原子性

所有限流算法（Token Bucket / Leaky Bucket / Sliding Window）的 `AllowN` 方法全程在同一把互斥锁内完成"判断 → 扣减"，不会出现 TOCTOU（Time-of-Check-to-Time-of-Use）竞态：

```
Goroutine A ──Lock()──[读tokens → 够 → 扣减 → return true]──Unlock()──
Goroutine B ──────────Lock()──[读tokens → 不够 → return false]──Unlock()──
                      ↑ B 必须等 A 释放锁后才能进入
```

**不可能** 出现两个 goroutine 都看到"剩余 1 个令牌"然后各自扣减成功的情况。

### 1.2 Manager 层：`sync.Map` + `LoadOrStore` 保证单例

当两个 goroutine 同时为同一个新 key 创建 limiter 时：

```
A: Load("tb:user1") → miss    B: Load("tb:user1") → miss
A: new limiterA                B: new limiterB
A: LoadOrStore → 存入 limiterA ✅  B: LoadOrStore → 发现已有，返回 limiterA (limiterB 被丢弃)
A: limiterA.AllowN(1) → 10→9  B: limiterA.AllowN(1) → 9→8
```

`LoadOrStore` 是原子 CAS 操作，保证任何 key 始终只有一个 limiter 实例存活。两个 goroutine 最终都在同一个 limiter 上竞争 Mutex，不会"双倍放行"。

唯一的代价是 `limiterB` 白创建了一次，很快被 GC 回收，可忽略。

## 2. 已知局限与设计取舍

### 2.1 单节点限制（最重要）

**现状**：当前是进程内限流，每个服务实例各自维护独立的 limiter。

**问题**：如果服务水平扩展为多实例，总放行量 = 限额 × 实例数：

```
            ┌─ 实例A (Manager, capacity=100) ─ 放行 100
用户请求 ───┤
            └─ 实例B (Manager, capacity=100) ─ 放行 100
                                                总共放行 200！
```

**解决方向**：
| 方案 | 思路 | 适用场景 |
|------|------|---------|
| Redis + Lua | 用 Redis 做集中式令牌桶（EVAL 脚本保证原子性） | 中小规模，延迟要求 <10ms |
| Redis Cluster | 分片 + Lua，横向扩展 Redis | 大规模 |
| 本地 + 全局混合 | 本地预取一批令牌（如 10 个），用完再去 Redis 申请 | 高性能 + 分布式兼顾 |
| 放弃精确 | 每实例限额 = 总限额 / 实例数，依赖服务发现感知实例数 | 能容忍误差时最简单 |

### 2.2 令牌浪费（Token Waste）

**现状**：限流器扣减令牌后立即返回 `Allowed=true`，客户端再去请求下游服务。

**问题**：如果下游请求失败（超时、5xx、网络断开），令牌已经扣了但没有真正"消费"下游资源：

```
t0  限流器扣令牌 (tokens: 10 → 9), 返回 Allowed=true
t1  客户端发起下游请求
t2  下游服务 500 ← 请求失败！
    令牌白扣了，但用户感知是"我没成功，为什么还算我一次"
```

**影响**：假设 100 个请求放行，30 个因下游故障失败，用户实际只成功 70 个，但限额已经用完。

**为什么可接受**：
1. 限流器的目的是**保护下游免于过载**，而非精确计量成功请求数。即使浪费了令牌，下游收到的请求量仍在限额内——保护目标达成。
2. 正常运行时下游成功率 99%+，浪费量可忽略。
3. 令牌桶会持续补充、滑动窗口持续滑动，影响只持续一个很短的周期。

**如果要解决**：
| 方案 | 做法 | 代价 |
|------|------|------|
| 令牌归还 | 失败后调用 `Return()` 归还令牌 | 并发复杂：归还的令牌 + 新补充的令牌可能超容量 |
| 后置扣减 | 先放行，请求成功后才扣令牌 | 瞬间突发无法控制，失去保护意义 |
| 预留+确认 | `Reserve() → Do() → Confirm()/Cancel()` 两阶段 | 实现复杂，性能开销大 |
| 容忍并调参 | 稍微调高限额（如设 110 来容忍 10% 浪费） | **最简单实用，生产中最常见** |

> Nginx、Envoy、Sentinel、Guava RateLimiter 都选择"容忍"策略。

### 2.3 非公平调度

**现状**：`sync.Mutex` 不保证 goroutine 的获锁顺序。

**问题**：高并发下，先到的请求不一定先获得锁：

```
请求到达顺序: A(t=0) → B(t=1) → C(t=2)
获锁顺序可能: C → A → B  ← 不公平
```

如果只剩 1 个令牌，可能最后到的 C 反而拿到了，而最先到的 A 被拒绝。

**为什么可接受**：
1. 限流器通常面向大量独立请求（不同用户/IP），不需要严格先来后到。
2. `sync.Mutex` 在 Go runtime 中有一定程度的反饥饿机制（等待超过 1ms 的 goroutine 会进入饥饿模式优先获锁）。
3. 公平锁的性能开销显著更高。

**如果要严格公平**：可以改用 channel 实现 FIFO 队列，或使用带时间戳排序的等待队列，但会牺牲约 2-5x 的吞吐量。

### 2.4 AllowN 的 All-or-Nothing 语义

**现状**：`AllowN(n)` 要么全部放行 n 个，要么全部拒绝。不会"部分消耗"。

**例子**：桶里有 10 个令牌，`AllowN(11)` 直接返回 false，令牌数不变仍是 10。

**为什么这样设计**：
1. `AllowN(n)` 通常代表**一个代价为 n 的原子操作**（如批量写入 n 条记录），部分消耗意味着"写了 10 条成功 1 条失败"，调用方很难处理。
2. 防止**大请求饥饿小请求**——如果大请求每次都"榨干"剩余令牌，`Allow()` 这样的小请求永远拿不到。
3. 拒绝后令牌保持不变，下一个小请求仍然能通过。

**如果需要"尽可能消耗"**：可以添加 `TakeAvailable(n) int` 方法，返回实际获取的令牌数。

## 3. 性能设计总结

| 设计选择 | 原因 |
|---------|------|
| 惰性计算（不用定时器） | `Allow()` 时按时间差补充令牌，避免后台 goroutine 和 timer 开销 |
| `sync.Mutex` 而非 `sync.RWMutex` | `Allow()` 既读又写，RWMutex 无收益反增开销 |
| `sync.Map` 而非 `map` + `RWMutex` | 读多写少的 key 查找场景，`sync.Map` 热路径无锁 |
| `float64` 令牌数 | 支持亚秒级精确补充，避免整数截断误差 |
| 零内存分配 | `Result` 是值类型，`Allow()` 不产生堆分配 |
| 环形数组（滑动窗口） | 固定 O(1) 内存，通过 `%` 取模复用空间 |
